# 文件预览的浏览器持久缓存

再次打开同一份文件时，直接读取浏览器里上次已经读过的数据，不再重复
「浏览器 → Worker → 存储」的每一次请求。首次打开的流程和请求数保持原样。

## 覆盖的文件类型

| 类型 | 预览 | 缓存方式 |
| --- | --- | --- |
| PDF | PDF.js 查看器 | 按分段，读过哪些存哪些 |
| Word、Excel、PPT（docx / xlsx / pptx） | 页内预览 | 整份文件 |
| 文本、Markdown、代码、HTML、URL 快捷方式 | 阅读与编辑器 | 整份文件 |
| 图片（含 HEIC / HEIF / AVIF） | 图片预览 | 整份文件 |

不缓存的类型及原因：

- 视频、音频：边播边取的流式数据，体积大，由播放器和浏览器自身的媒体缓冲处理。
- Flash、终端录像（asciinema）、种子、压缩包内容、安装包：由第三方播放器自行下载，
  或内容来自接口而非文件本身。
- 管理员配置的外部 iframe 预览（如在线 Office 服务）：文件由第三方服务读取。
- 文件夹说明（README）：属于目录信息，不是打开的文件。

## 为什么之前每次都慢

PDF 预览按 64 KiB 分段读取，打开一份文档通常需要二三十次 Range 请求，其中不少
必须串行（先读目录，才知道下一段在哪）。为避开 Chromium 对同 URL 分段请求的排队，
这些请求在浏览器和 Worker 两侧都是 `no-store`（见
[PDF 首屏加载与 Range](pdf-preview-loading.md)），所以关掉再打开就要全部重来。
Office、文本和图片预览每次也重新下载整份文件；文本请求还带有时间戳参数，
开启链接有效期时签名每次不同，浏览器自身的 HTTP 缓存都无法命中。

## 策略

| 项目 | 做法 |
| --- | --- |
| 存放位置 | 浏览器 IndexedDB（库名 `openlist-document-cache`），按 64 KiB 分块 |
| 缓存键 | 账号 ID、文件路径、大小、修改时间；不含下载签名，签名变化仍然命中 |
| PDF | 读过的分段写入缓存；再次打开时初始请求与已缓存的分段都不发往网络，没读过的页仍按需请求并补入缓存 |
| 其他类型 | 整份文件连同内容类型写入缓存，再次打开直接读取；写入前的下载绕过浏览器 HTTP 缓存，避免把旧内容存到新文件名下 |
| 容量 | 合计 256 MiB、200 份、30 天未使用即清理；单份最多 128 MiB，超出的部分只走网络；按最近使用淘汰 |
| 退出登录 | 清空全部缓存 |

缓存只存在于当前浏览器，不经过服务器，也不改变 Worker 的下载鉴权：打开文件前
仍然先请求文件信息，没有权限的文件拿不到预览。

## 文件被替换时

- 文件被覆盖后大小或修改时间会变化，缓存键随之变化，旧数据不会再被读取，并在
  之后按最近使用规则清理。
- 没有有效修改时间的存储、压缩包内的文件、大小未知的文件不缓存。
- 列表信息与实际内容不一致时的兜底：只要有请求发往网络，就核对总长度以及同源
  响应的 `ETag` / `Last-Modified`。不一致时删除这份文档的缓存；如果本次已经用过
  缓存数据，查看器通知页面并自动重新加载一次，这一次完全走网络。
- 文件信息里的大小与服务器返回的大小不同，该文件不写入缓存。
- 整份缓存的文件（Office、文本、图片）命中后不再发请求，因此完全依赖列表信息。
  经本站上传、编辑器保存、改名、移动都会立即刷新列表信息；绕过本站直接改动
  存储时，旧内容最多保留到目录缓存过期（本部署为 5 分钟）或手动刷新。
- 切换文件时，上一份尚未完成的下载会被取消，不会写入缓存。

## 失败时的回退

缓存不能成为文件打不开的原因：

- 带缓存打开 PDF 失败时，查看器先删除这份文档的缓存，页面随即不带缓存自动重开
  一次；仍然失败才显示错误，并附上错误类别（不含地址和签名），便于排查。
- IndexedDB 在 2 秒内没有响应（Safari 上出现过请求一直挂起的情况）时，本次打开
  直接走网络，不等待缓存。

## 查看器更新后的旧页面

查看器路径带修订号（当前 `6.3.289-openlist6`），每次修改都会变化。更新前就打开
着的页面仍在请求上一个修订号的路径，而该路径在部署后不再存在，表现为预览区
空白、约 30 秒后提示加载失败，并且「重试」无效，需要整页刷新。

页面现在会在查看器加载完成时检查入口是否有效；无效时按「页面资源已更新」处理：
没有进行中的上传时自动刷新一次，否则显示「重新加载页面」。这项检查随新页面
生效，对更新前已经打开的页面不起作用，那些页面仍需手动刷新一次。

## 浏览器版本过旧

内置的 PDF.js 6.3.289 在启动时就需要 `Promise.withResolvers` 和 `AbortSignal.any`
（Safari / iPadOS 17.4 起提供），其「legacy」发行包没有为它们提供替代实现；样式
还大量使用 `light-dark()`（Safari 17.5）和 CSS 嵌套。在更旧的浏览器上查看器无法
启动：预览区只剩一个未加样式的页码输入框，随后提示加载失败。这与缓存无关，
在加入缓存之前的查看器上同样出现。

页面现在先检查这两项能力，不满足时不再加载查看器，直接说明所需版本并提供
「用浏览器打开 PDF」，由浏览器自带的阅读器显示。查看器启动失败时，错误提示
会附上启动阶段的错误信息（此时尚未打开文件，不含文件地址）。

## 适用范围与限制

- 只对「重新打开」有效；首次打开、换浏览器或换设备仍需从网络读取。
- 无痕窗口、存储空间不足或 IndexedDB 不可用时自动退回原来的网络读取，预览不受影响。
- 跨域直链需要对方暴露 `Content-Range` 才会缓存 PDF 分段，否则保持原行为。
- 图片直链所在的域不允许脚本读取（未配置 CORS）时，图片按原地址直接显示且不缓存；
  同一页面内之后不再对该域尝试。
- 缓存不可用或下载失败时，各预览退回原来的请求方式和错误提示。
- 查看器静态文件（PDF.js 本身）的缓存由部署平台的静态资源策略决定，不在本次范围内。

## 本地对比

真实 Chromium、完整查看器、24 页约 3.2 MB 的测试 PDF，每个文件请求在响应头前
人为延迟；计时为从开始加载页面到当前页渲染完成。

| 单次延迟 | 原行为（每次打开） | 首次打开 | 再次打开 | 再次打开的文件请求 |
| -------- | -----------------: | -------: | -------: | -----------------: |
| 300 ms   |             2.8 s |    2.8 s |   0.35 s |                  0 |
| 2 s      |            16.4 s |   16.4 s |   0.35 s |                0–1 |

2 秒一行中的 1 次请求是上次关闭时还没读完的相邻页分段。以上是本地可控延迟环境
的结果，不是线上 B2 的实测；线上收益取决于回源延迟，可在 Network 面板确认再次
打开时不再出现该文件的请求。

## 实现位置

- `scripts/pdf-range-cache.mjs`：缓存本体，随查看器部署为 `web/openlist-cache.mjs`。
- `scripts/fetch-pdf-viewer.mjs` 的 `patchPdfRangeCache()`：让 PDF.js 的文档请求
  经过可选的缓存钩子；预期代码不匹配时构建失败。
- `scripts/pdf-viewer-bridge.mjs`：从握手消息取得文件身份并开启缓存。
- `frontend-patches/document-cache.patch`：页面侧生成文件身份并传给查看器，
  Office、文本、图片预览接入，退出登录时清理。

查看器集成修订号随之升为 `6.3.289-openlist6`。

## 回归

`pdf-persistent-cache.test.mjs` 使用真实 Chromium 与部署后的查看器，不拦截请求，
覆盖：再次打开零请求且签名变化仍命中、未读页按需补取、小于 Range 阈值的文件、
身份变化不复用、内容变化后的清理与通知、大小不一致时不缓存、无身份时保持原行为、
整份文件读写、内容类型与淘汰。`frontend-document-cache.test.mjs` 覆盖文件身份的
生成规则、页面与查看器路径的一致性，以及各预览的接入方式。两者均已加入构建流程。
