# PDF 首屏加载与 Range

PDF 预览使用本地部署的 PDF.js 6.3.289 legacy viewer。`disableRange=false`、
`disableStream=true`、`disableAutoFetch=true`，保留默认 64 KiB 分段。
搜索、打印、下载或文档恢复仍可能读取更多数据；无 Range 的源站自动回退普通下载。

## 高延迟对比

2026-09-30 使用实际 Chromium 与完整预览器测试同一份 24 页、约 38.8 MB 的 PDF。
两种目录布局分别是平铺 `/Pages` 与增加一级嵌套 `/Pages`，页面内容保持相同。
每条文件请求在响应头前延迟 2 秒，传输速率限制为 8 MiB/s；测试使用独立浏览器
上下文，观察第一页 canvas 渲染完成。首屏后的字节量是固定 200 ms 观察窗口的
服务端发送量，可能含相邻页正在进行的读取，不能当作闲置后的最终下载量。

| 目录布局 |    分段 | 首屏时间 | 观察窗口发送量 | Range 请求数 |
| -------- | ------: | -------: | -------------: | -----------: |
| 平铺     |  64 KiB |   17.0 s |        3.11 MB |           27 |
| 平铺     | 256 KiB |   17.2 s |        7.83 MB |           27 |
| 平铺     | 512 KiB |   17.3 s |       14.12 MB |           27 |
| 平铺     |   1 MiB |   15.5 s |       26.18 MB |           26 |
| 嵌套     |  64 KiB |   55.2 s |        3.11 MB |           27 |
| 嵌套     | 256 KiB |   55.8 s |        7.83 MB |           27 |
| 嵌套     | 512 KiB |   56.6 s |       14.12 MB |           27 |
| 嵌套     |   1 MiB |   56.1 s |       26.18 MB |           26 |

扩大分段没有消除目录解析的等待，增加了请求覆盖的数据，因此没有采用。

## 修复

1. `scripts/fetch-pdf-viewer.mjs` 在校验原始发行包 SHA-256 后，对固定版本 worker
   的 `Catalog.getPageDict()` 做小范围构建期修正。PDF.js 在文档加载完成前校验
   最后一页；当目标是一个计数有效的目录节点的最后一页时，并发读取这个节点中
   遍历原本就需要的页字典，复用原来的缓存、遍历和错误校验。首次/任意页的
   嵌套节点读取继续按需执行。取消或错误导致遍历提前退出时，尚未消费的 promise
   也不会产生未处理拒绝。原始代码出现变化或重复匹配时，安装失败。
2. `src/backend/server/raw.ts` 将针对 B2 视频 Range 的 `fetch(cache: "no-store")`
   同样应用于 PDF Range，避免分段读取落入整文件缓存回源路径。限制仍是 B2
   主机、视频/PDF、实际带 Range 三项同时满足；普通下载、图片、其他存储和
   不支持 Range 时的重试沿用原策略。签名、SSRF 校验和 Range 原样透传。
3. 静态目录升级为 `6.3.289-openlist2`，使入口与 worker 一起更新。

在最终安装产物上重复比较，仍使用 64 KiB：

| 目录布局 / 单次延迟 | 修复前首屏 | 修复后首屏 |
| ------------------- | ---------: | ---------: |
| 嵌套 / 2 s          |    55.16 s |    18.87 s |
| 平铺 / 2 s          |    16.90 s |    16.91 s |
| 嵌套 / 50 ms        |     2.46 s |     1.35 s |
| 平铺 / 50 ms        |     1.22 s |     1.26 s |

2 秒延迟时，两种布局修复前后的发送量与 27 次 Range 请求数完全相同。
以上是可控延迟环境的本地证据，并非用户实际 B2 文件的线上计时；真实改善取决于
目录布局、回源延迟和浏览器连接并发。B2 缓存策略通过签名代理的 HTTP 层回归验证，
实际 Cloudflare 命中情况仍需上线后观察 Network Timing 与响应头。

## 回归

`fetch-frontend.mjs` 安装查看器后执行 `pdf-page-tree.test.mjs`，直接从最终 worker
提取并执行实际方法，验证嵌套目录的并发、首次/任意页的按需读取、缓存复用、
异常计数、循环引用和错误传播。Build Verify 同时执行 `b2_video_range.test.ts`，
验证视频/PDF 的签名、206、原始 Range 与缓存策略。
